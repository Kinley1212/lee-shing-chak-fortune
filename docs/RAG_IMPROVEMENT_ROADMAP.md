# RAG 改進路線圖

## 1. 目前架構

項目目前使用混合式 RAG：

1. 識別生肖、主題、身份問題及卦名等確定性 metadata。
2. 問題包含足夠資料時，先用 metadata 限制候選範圍。
3. 使用中文關鍵字和 Gemini 語義向量為候選片段排序。
4. 拒絕低於相關度門檻的弱語義匹配。
5. 把來源及頁碼 metadata 加進檢索內容。
6. 將檢索片段連同用戶問題交給 Gemini 2.5 Flash 生成回答。

目前知識庫包含：

- 254 個《2026全書》片段。
- 63 個北帝靈籤片段。
- 合計 317 個預先計算的文件向量。
- 每個向量 768 維。

固定運勢報告繼續使用確定性的生肖及主題 metadata，不需要為每個報告段落呼叫查詢 embedding。自由問答在 metadata 不足時才使用語義檢索。

## 2. Gemini Embedding

Gemini Embedding 是 Google Gemini API 提供的專用 embedding 模型。它與負責生成回答的 Gemini 2.5 Flash 是兩個不同模型，但都透過同一個 `google-genai` SDK 呼叫，亦可使用同一組 Gemini API Key。

本項目使用：

- `gemini-embedding-001` 生成文件及查詢向量。
- 建立文件索引時使用 `RETRIEVAL_DOCUMENT`。
- 處理用戶查詢時使用 `RETRIEVAL_QUERY`。
- 最終回答由 `gemini-2.5-flash` 生成。

Embedding 會將文字轉成代表語義的數字向量。即使兩段文字沒有使用相同詞語，只要意思接近，其向量方向通常也會接近。檢索器使用 cosine similarity 比較查詢向量和文件向量。

文件向量由 `scripts/build_embedding_index.py` 預先生成，保存在 `data/knowledge/embedding_index.json`。網站運行時只需為新的用戶問題生成查詢向量，不需要每次重新向量化整本書。

## 3. 目前相關度門檻

目前語義門檻為 `0.62`：

```env
RAG_MIN_SEMANTIC_SCORE=0.62
```

這是針對目前知識庫設定的暫定值，不是 Gemini 官方標準，也不代表 62% 正確率。初步真實資料測試大致得到：

| 問題類型 | 示例 | 最佳相似度 |
|---|---|---:|
| 有關事業 | 廣東話詢問轉工 | 0.71 |
| 有關健康 | 廣東話詢問身體不適 | 0.73 |
| 有關風水 | 廣東話詢問家居氣場 | 0.68 |
| 知識庫範圍以外 | 量子力學問題 | 0.50 |

`0.62` 位於目前觀察到的相關和無關分數之間。生肖＋主題的精確 metadata 匹配不受此門檻限制，因為它是確定性匹配，不是推測性的語義匹配。

日後應使用更大的標註評測集重新校準，不能長期只依賴少數測試問題。

## 4. 建議改進

### 目前完成狀態（2026-08-11）

已完成：

- 建立 56 條標註評測，包含精確生肖主題、口語語義、缺資料追問、特殊路由及範圍外拒答。
- 加入可重複執行的 `scripts/evaluate_rag.py`，目前評測為 56/56 通過。
- 使用 Reciprocal Rank Fusion 融合關鍵字和語義候選排序。
- 加入主題同義詞、廣東話表達及對話歷史生肖補全。
- 個人流年缺少生肖時先追問，不直接生成通用答案。
- 無證據通過門檻時停止生成，避免把模型常識冒充成書本內容。
- 後端回傳結構化引用，聊天介面直接顯示來源、主題、生肖及可用頁碼。
- 精確生肖＋主題命中後立即返回，不再為湊滿 Top-K 混入其他主題。
- 加入不記錄原始問題和個人資料的檢索 metadata、分數與延遲記錄。
- 加入 `scripts/audit_knowledge_chunks.py` 檢查片段長度、缺失 metadata 和重複內容。

目前數據審計顯示，片段長度及重複情況沒有迫切問題，因此暫不重切全部內容；主要資料缺口是頁碼 metadata 不完整。專用模型 Reranker 亦暫不加入，因為現有評測已全部通過，額外模型呼叫暫時缺乏可量化收益。

### 第一階段：建立標註評測題庫

這是最高優先級，因為後續所有修改都需要可量化的比較基準。

建立 50–100 條具代表性的問題，涵蓋：

- 正式書面語和廣東話口語。
- 同義詞、短問題、錯別字及間接表達。
- 有生肖及沒有生肖的問題。
- 同時涉及多個主題的問題。
- 身份和具名卦象問題。
- 知識庫沒有答案的問題。
- 明確超出玄學知識庫範圍的問題。

每條測試應標註：

- 預期意圖和主題。
- 適用時的預期生肖。
- 正確來源片段或可接受片段。
- 是否應先追問補充資料。
- 是否應拒絕聲稱答案來自書本。
- 回答中禁止出現的錯誤資訊。

至少追蹤以下指標：

- 主題分類準確率。
- Top-1 和 Top-3 檢索命中率。
- 錯誤生肖引用率。
- 範圍外問題拒答準確率。
- 引用來源準確率。
- 最終回答有證據支持的比例。

利用正確和錯誤候選片段的分數分布重新校準語義門檻，在「漏掉有用片段」和「放入無關片段」之間選擇適合業務的平衡點。

### 第二階段：改善知識片段質量

檢索效果的上限由原始片段質量決定。應按自然段落和語義邊界重新切分知識庫，而不是只按固定長度切割。

建議：

- 每個片段只保留一個主要主題。
- 保留標題、生肖、章節及頁碼。
- 移除頁眉頁腳、重複文字、OCR 雜訊和破損連結。
- 避免在句子或清單中間切斷。
- 只有上下段確實互相依賴時才加入少量重疊。
- 分開通用建議和生肖專屬內容。
- 需要準確引用時保留原書文字，不讓模型預先改寫。
- 驗證每個片段都能追溯到真實來源頁碼。

重新切片後必須重建 embedding 索引，再用同一套評測題庫比較結果。

### 第三階段：加入候選融合和 Reranker

目前系統直接加權語義分數和關鍵字分數。Reranker 可以更深入地比較完整問題與每個候選片段。

建議流程：

1. Metadata 過濾有效範圍。
2. 關鍵字和語義檢索各自找出 10–20 個候選。
3. 使用 Reciprocal Rank Fusion 或加權融合合併候選名單。
4. Reranker 對問題與候選片段重新評分。
5. 只把最佳 3–5 段交給生成模型。

初期可使用 Gemini 做輕量 rerank，再透過評測確認是否值得增加一次模型呼叫。只有證明有明顯收益後，才考慮專用 reranking 服務。

生肖＋主題已精確匹配的固定報告不應執行 rerank，避免增加延遲和成本。

### 第四階段：問題改寫和資料不足追問

檢索前可以將口語問題整理成簡潔的搜尋查詢，同時保留原始問題供最終回答使用。

例如：

```text
原問題：我今年有冇機會搵多啲錢？
檢索問題：2026年財運、收入及投資機會
```

```text
原問題：成日瞓得唔好有冇嘢要注意？
檢索問題：2026年健康運、睡眠及精神狀態注意事項
```

如果個人化回答依賴缺失資料，系統應先追問，而不是使用通用內容或任意生肖內容。例如用戶沒有提供出生年份或生肖，卻詢問個人流年時，應先請用戶補充資料。

問題改寫不能過度，否則可能改變用戶原意，因此亦需納入評測。

### 第五階段：在前端顯示引用來源

目前檢索內容已包含來源和頁碼，但最終介面應直接顯示證據：

```text
參考資料
《2026全書》第112–113頁
屬龍・事業運勢
```

後端應將引用資料以結構化欄位和回答正文分開回傳，前端再顯示於相關答案下方，方便用戶及維護人員核對回答依據。

頁碼和來源必須直接來自檢索片段的 metadata，不能讓語言模型憑記憶生成。

### 第六階段：增加回答依據檢查

回答送出前檢查重要內容是否受到檢索證據支持：

- 沒有片段通過門檻時，不得聲稱內容來自書本。
- 生肖專屬內容必須和用戶生肖一致。
- 星曜、日期、方位和化解方法應出現在檢索證據中，否則要明確標示為一般分析。
- 證據互相衝突時，應說明不確定性，不能默默選擇其中一段。
- 醫療、財務等影響較大的內容應保留適當提示和限制。

生肖、來源和頁碼一致性優先使用程式規則檢查。只有評測證明有實際價值時，才加入額外的模型驗證呼叫。

### 第七階段：改善監控和用戶反饋

在不儲存不必要個人資料的前提下記錄：

- 識別出的主題和生肖。
- 候選片段 ID 及檢索方法。
- 關鍵字、語義及最終分數。
- 是否使用回退或追問。
- 回答延遲及 embedding 錯誤。
- 可選的用戶有用／無用反饋。

利用這些資料找出常見失敗問題，擴充主題同義詞和評測題庫。除非已有明確的保留和私隱政策，否則不應記錄完整出生資料、電郵地址、API Key 或未遮蔽的個人問題。

## 5. 現階段不需要的改動

目前只有 317 個向量，使用記憶體直接搜尋已經足夠快。單純換成 Pinecone、Chroma 或其他外部向量資料庫，不會自動提高回答質量。

暫時亦不應只為增加複雜度而加入知識圖譜或多 Agent 檢索架構。出現以下情況時才重新考慮外部基礎設施：

- 知識庫增長至數萬個片段。
- 多本書或多個客戶需要隔離索引。
- 內容需要持續更新且不能重新部署。
- Metadata 過濾和權限控制變得複雜。
- 記憶體或檢索延遲成為實際營運問題。

## 6. 建議執行順序

1. 建立並自動運行標註評測題庫。
2. 清理原始資料並按語義重新切片。
3. 根據評測結果校準相關度門檻。
4. 加入候選融合和 Reranker。
5. 加入問題改寫及生肖資料不足追問。
6. 後端回傳並在前端顯示結構化引用。
7. 加入回答依據檢查和檢索監控。
8. 再評估是否真的需要外部向量資料庫。

每個階段都必須使用同一套評測集比較。只有當修改能提高檢索或回答質量，而且延遲、成本及固定報告回歸風險仍可接受時，才保留該修改。
